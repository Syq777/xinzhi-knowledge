**以下为作者观点：**

整个科技行业，正在发生一场悄无声息的转变。

质量保证（QA）角色正从企业组织架构中消失，QA工程师被解雇，整个QA团队要么被并入工程部门，要么被彻底解散。领英上，“QA分析师”或“软件测试员”之类的职位头衔逐渐淡出，取而代之的是自动化相关的热门词汇和以开发为中心的表述。

为什么？因为现代开发文化让公司相信，开发人员可以而且应该负责测试。平心而论，他们并没有错。但他们犯了一个严重的错误：他们混淆了测试和质量。

随着QA的消失，质量成了每个人的问题。但当开发者负责测试时，到底谁来掌控质量？谁来制定策略、管理风险、把握全局？

测试是一项任务，质量是一种文化

人们常常把QA等同于手动测试、点击用户界面，或者验证漏洞修复。但这种观点早已过时且过于片面。QA关乎风险管理、用户共情、系统思维和反馈循环。测试只是这一大拼图中的一块而已。

有人认为，我们根本不需要专门的角色，他们说“我们都是工程师”。虽然协作至关重要，但角色的存在是为了带来专注和深度。

产品经理专注于愿景，开发者专注于构建，QA工程师则专注于产品在压力下的表现以及给用户带来的体验。

角色不同，使命一致。不过，需要明确的是：开发者应该编写测试。

单元测试、集成测试、API契约测试，这些都是工作的一部分。自动化已不再是可选项。但仅凭测试无法保证软件质量。测试只能确保代码按指令运行，却无法保证它符合用户的期望。这正是QA从不只关乎测试的原因所在。

- QA工程师思考的是系统，而不只是功能。
- 他们会问，这里存在什么风险？
- 他们关注的是用户行为，而不只是代码分支。
- 他们建立的是信心，而不只是覆盖率。


当QA消失后，这些无形的质量层面往往也会随之消失。突然间，漏洞就出现在了生产环境中，不是因为没人测试，而是因为没人像质量架构师那样思考。

当开发者负责测试时会发生什么？

企业犯的错误并非让开发者承担更多测试责任，而是认为裁撤QA就意味着不再需要质量思维。

将测试转移给开发者可以提高速度和责任感，但也带来了新的挑战：

1. 偏向“顺利路径”：开发者往往测试自己所构建的部分，而不是它会如何出错。

2. 视野局限：没有QA的整体视角，边缘情况和系统级故障就会被忽略。

3. 失去探索性测试：自动化无法完全取代人类的好奇心。真实用户会做出意想不到的事情，QA也应该如此。

4. 没时间制定策略：开发者面临着交付压力，编写和维护测试只是众多优先事项之一。质量策略很少能得到应有的关注。

那么问题来了：如果每个人都负责测试，谁来负责质量？

质量架构师应运而生

团队有时会陷入追求100%测试覆盖率或自动化一切的误区。但真正的QA明白：

“并非所有能测试的都应该测试，并非所有能自动化的都应该自动化。”

关键在于价值而非数量。像Cypress、Playwright和Jest这样的工具很棒，但只有在有明确策略和目的的情况下使用才有效。Dropbox就因注重编写有价值且可维护的测试，而非仅仅增加测试数量而闻名。

随着传统QA角色从企业组织架构中逐渐消失，一种新的混合型角色正在崛起。他们不是QA，不是测试员，也不是开发者，而是既了解开发又懂质量，能够弥合代码与信心之间差距的人。

我们称之为质量架构师。这不是一个只会点击按钮或编写测试用例的人，而是一个通过设计系统（而非仅仅是脚本）来大规模构建信任的人。

质量架构师的职责包括：

质量策略与架构：

• 定义并逐步完善跨栈质量策略，涵盖从单元到用户界面、端到端再到生产监控的各个层面。

• 管理基于风险的测试方法：关注影响，而非仅仅是覆盖率。

• 设计测试自动化架构：自动化层级、仓库结构、环境、流水线。

• 指导团队保持适当的自动化平衡（测试什么、不测试什么、原因及方式）。

• 在各个项目和服务中推动测试的可扩展性、可维护性和性能。

跨职能协作：

• 与产品、设计和工程团队合作，在代码编写之前尽早识别风险。

• 将质量思维融入规划、待办事项细化和设计讨论中。

• 弥合不同角色之间的沟通差距，确保用户体验、功能和可靠性保持一致。

指导与文化引领：

• 讲解质量实践背后的“原因”，不仅是如何测试，还包括测试为何重要。

• 指导开发者掌握测试策略，以及如何在工作流程中提前关注质量。

• 倡导共同的质量理念，帮助团队将QA视为战略合作伙伴，而非仅仅是一个阶段。

• 规范探索性测试、用户体验测试和基于风险的优先级排序等实践。

工具与AI赋能：

• 主导AI驱动的测试工具（如用于测试生成、漏洞检测、分析的工具）的评估和采用。

• 制定AI生成代码/测试的管理规范，确保输出可信、可追溯且可维护。

• 优化测试环境和数据，以支持智能、稳定的自动化。

指标、可观测性与反馈循环：

• 跟踪关键质量指标：缺陷逃逸率、测试可靠性、覆盖质量、周期时间等。

• 构建质量健康状况和风险可见性的仪表板和可视化工具。

• 将生产环境的反馈（如日志、崩溃信息、支持工单）整合到未来的测试策略中。

• 连接漏洞、用户体验、业务影响和长期可维护性之间的关联。

质量架构赋能：

• 定义测试仓库结构、自动化类型（单元、API、端到端）和所有权模型。

• 创建框架和工具，使开发者能够高效测试，同时不拖慢进度。

• 提供用于CI/CD集成、并行执行和测试数据管理的可扩展模式。

简而言之，质量架构师不是来编写每一个测试的，而是来设计一个能让质量在大规模场景下得以实现的系统。

他们是：

• 战略合作伙伴

• 教育者

• 系统思考者

• 质量倡导者

• AI赋能者

• 用户信任的守护者

这是一个基于经验、共情和工程判断的角色，而这也正是QA工程师注定要进化成的样子。

但事实是：将测试转移给开发者并不意味着要取消QA，而是意味着我们需要重新定义它。更重要的是，我们需要对团队进行培训。因为我们都在朝着同一个方向努力：交付更好的产品、更快地迭代、减少风险，而不只是被动应对风险。

把QA当作一个勾选框或事后才考虑的事情，我们无法实现这一目标。我们需要建立跨职能的质量责任制，让质量架构师处于核心位置，指导策略制定、提高质量标准，确保质量能随着代码库一同扩展。

这意味着QA角色正在演变。核心技能，如批判性思维、好奇心和系统思维，比以往任何时候都更加重要。所需要的是身份上的转变。

结论

QA 2.0将致力于提升质量作为一门学科的地位，并将QA工程师转变为领导者、战略家和架构师。因为质量的未来不属于任何单一角色，而属于那些勇于承担责任的人。

诚然，质量是每个人的责任，但仍然需要有人来构建架构，使质量具有可扩展性、可持续性并成为现实。这就是质量架构师的作用：不是守护大门，而是指引方向。

没错，开发者应该进行测试。但更重要的是，每个人都应该关注质量。让我们开始将质量视为连接愿景与执行、代码与信心以及团队与用户的粘合剂。随着测试不断前置，让我们确保质量不会被忽视。

而QA工程师们？他们不是被排挤出去，而是被召唤去领导、去制定策略、去在满是代码提交的环境中成为用户的代言人。但团队需要愿意倾听这些声音。

所以，如果你的职位头衔正在消失，不要惊慌，要进化——成为质量架构师。因为质量依然重要，而且需要有人来负责。
