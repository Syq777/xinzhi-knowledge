#### 引言

近年来，Prompt Engineering（提示工程）曾是构建 LLM 应用的核心技能：你需要写出最合适的提示 (system prompt + few-shot 示例)，以引导模型完成任务。但随着我们开始构建更复杂、更自治 (agentic) 的系统 — 比如能循环调用工具、长期执行任务的 AI agents — 这个范式逐渐暴露出瓶颈：上下文窗口有限、对话历史积累过多、任务跨度过长。

Anthropic 在其技术博客中提出并系统阐释了一个更宏观的概念：**上下文工程 (Context Engineering)**。它不仅仅是写提示，而是设计、管理、优化整个上下文状态，以最有效地利用模型的“注意力预算 (attention budget)”。本文将介绍这一方法的核心原则，以及如何在工程实践中落地。

#### 什么是上下文工程

上下文工程 (Context Engineering) 是指一系列策略，用来策划和维护 LLM 推理过程中包含的信息 (tokens)，这些信息不仅限于提示 (prompts)，还包括工具定义 (tool specs)、对话历史、外部数据、模型协议 (如 MCP) 等。Anthropic 将其视为 Prompt Engineering 的自然进化。

为什么需要它？因为在构建 agent 时，我们面对的是 **不断增长** 的上下文状态：每一步交互、每一次工具调用、每个外部数据注入，都可能产生新的 token。如果不精心管理，这些内容会淹没模型，导致模型丧失焦点 (context rot) 或效率低下。

#### 上下文工程的关键原则

1. **最小但高信号 (High-signal) 信息集**


- 我们应始终追求 “尽可能少但最关键 (signal)” 的 token 集合，从而提升模型执行我们期望行为的概率。
- 增加无关或冗余 token，只会消耗注意力资源，降低性能。


1. **系统提示 (System Prompt) 的 “最佳高度 (Goldilocks 区)”**


- 提示不应过于硬编码 (如一大堆 if-else)，那样脆弱且难以维护。
- 也不应太宽泛，以假设模型或 agent 已经“知道很多上下文”。
- 最佳是语义清晰、直白，并且提供行为指导 +边界 (heuristics) 而不是严格逻辑。


1. **结构化提示 (prompt structuring)**


- 使用分段 (sections) 组织你的提示。例如：<background_information>、<instructions>、## Tool guidance、## Output description 等。
- 结构化提高可维护性，也帮助模型更好理解不同类型的信息。


1. **示例 (Few-shot)**


- 示例仍然非常重要，但不要试图覆盖所有边缘情况。
- 推荐选择 “典型但代表性 (canonical)” 的例子，这样模型能学习正确的行为模式，而不是被复杂异常情况干扰。


#### 高效工具 (Tool) 设计

- **清晰契约 (contract)**：每个工具应定义明确的输入参数 (descriptive, unambiguous)，以及预期输出。
- **高 token 效率**：返回给 agent 的信息应该紧凑、有用，避免冗长。
- **避免重叠功能**：工具之间功能过度交叉会导致 agent 决策不明确。
- **设计示例** (few-shot): 在工具使用提示中加入有限但具有代表性的示例，帮助 agent 理解用途和边界。


#### 运行时 (Just-in-time) 上下文策略

传统做法是预先检索所有相关数据 (例如 embedding 检索)，然后一次性放进上下文。但这种方式可能浪费大量 token，也可能加载不必要的信息。Anthropic 提出了 **just-in-time 加载** 的思路：

- 保持轻量级的标识符 (ID)：比如文件路径、查询、链接，而不是把整个内容都 preload。
- 在运行时，通过工具 (tools) 动态读取相关内容。Claude Code 就是这样做的：它用 Bash 命令 (head, tail) 检查文件，而不是把整个文件加载。
- 利用 **元数据 (metadata)**：文件名、层级 (folder)，时间戳等都能给 agent 提供重要线索 (重要性、用途等) 。
- **渐进披露 (Progressive Disclosure)**：agent 通过探索渐渐“发现”上下文，把最相关的信息保存在工作记忆 (working memory)，而不是一次性加载所有内容。
- 权衡：这种策略比预加载慢，而且需要 agent 有足够智能 (启发式 +工具) 去导航。但优点显著：减少上下文污染 (context pollution)，提高长期运行效率。
- **混合策略 (Hybrid)**：部分关键内容预加载 (preload)，剩余部分由 agent 运行时检索。Anthropic 就建议这种做法。
- **Claude Code 的混合方法**：例如，CLAUDE.md 文件预加载；而文件系统探索 (如查找特定文件) 则由 agent 自己动用 primitives (glob/grep) 完成。
- 对于对内容变化不太频繁 (如法律、金融) 的场景，这种混合加载特别适合。


#### 长时任务 (Long-horizon) 的上下文管理

对于跨越很长时间 /大量交互 (例如几个小时、复杂项目) 的任务，仅靠上下文窗口是难以支撑的。Anthropic 提出了三种策略：

**1. 压缩 (Compaction)**

- 当对话或上下文接近窗口上限时，先把历史内容总结 (summarize)，然后开启新的上下文窗口。
- 例如，Claude Code 会让模型总结架构决策、未解决问题 (bugs) 等关键信息，同时移除冗余的工具调用结果。
- 调优关键：保持高召回 (recall) → 确保不漏关键内容，再逐步调节精度 (precision) → 去除冗余。
- 风险：压缩得太厉害可能丢关键信息；压缩得太保守，又不能显著节省 token。


**2. 结构化笔记 / Agent 记忆 (Agentic Memory)**

- Agent 定期把重要信息写到持久化存储 (memory)，而不是全部存上下文。
- 后续需要时再把笔记 pull 回上下文。
- 例子：Claude Code 维护 NOTES.md，记录任务进展、依赖、决策路径等。
- 非代码场景也适用：Anthropic 讲到游戏代理 (agent) 在玩游戏时能记住状态、目标、策略，重启对话后继续。
- Anthropic 的 Memory 工具 (在 Claude Developer Platform 上) 支持这种结构化记忆。


**3. 子代理 (Sub-agent 多 Agent 架构)**

- 主 agent 负责高层决策、调度；子代理 (sub-agent) 专注具体任务 (如深度检索、分析、工具调用)。
- 子代理可以使用非常大的上下文 (tokens) 来处理细节，然后返回浓缩 (distilled) 的结果 (总结报告，大致 1,000–2,000 tokens)。
- 这样可以避免主 agent 被大量细节淹没，同时还保留子任务的深入能力。
- Anthropic 表示这种模式在复杂研究任务中效果很好。
- 根据任务类型选策略：
- 对话 / 交互任务 → 压缩 (compaction)有里程碑 / 清晰进展阶段 → 结构化笔记复杂分析、研究型任务 → 多 agent 架构


#### 工程落地建议

- 从最简单、最基础做起 —— 先构建一个最小可行 agent：最基本的系统提示 +少量工具。
- 通过实际任务驱动迭代：收集失败案例 (failure mode)、调优提示、示例、上下文压缩策略等。
- 使用 Anthropic 提供的平台 /工具 (例如内存工具) 来管理长期上下文。
- 实践混合策略 (预加载 + 即时检索 + 压缩)，并根据任务特点不断调整。
- 构建度量 (metrics)：例如上下文 token 使用量、工具调用次数、任务成功率、延迟等。


#### 未来展望

随着模型越来越强 (context 窗口越来越大，自主能力增强)，我们可能对人工设计 (engineering) 的依赖减少。但即使如此：

- 注意力 (attention) 仍然是有限资源：上下文管理永远是核心问题。
- 多 agent 系统 (Sub-agent 架构)、长期记忆 (Memory)、动态检索 (Just-in-time) 将是未来的关键构建块。
- 上下文工程 (Context Engineering) 将成为构建可靠、可扩展、高效 AI agent 的基础能力。


#### 结语

Anthropic 提出的 “上下文工程” 概念，标志着 LLM 开发从 “写好 prompt” 向 “构建智能上下文系统” 的转变。对于构建 agent 的工程师而言，这是一条非常现实且必经的进化路径。在你下一个 Agent 项目中，不妨尝试引入这些策略：压缩历史，结构化记忆，just-in-time 加载，以及子代理架构。上下文是宝贵资源，让我们设计得更聪明。
