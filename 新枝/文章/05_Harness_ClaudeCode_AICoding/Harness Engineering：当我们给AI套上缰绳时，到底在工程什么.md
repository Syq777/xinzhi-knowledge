# Harness Engineering：当我们给 AI 套上缰绳时，到底在工程什么

> 一个被反复引用的事实：OpenAI 内部一支 3–7 人的小团队，五个月里让 AI 生成了近百万行生产级代码，全程几乎没人手写业务逻辑。它的意义不在于"AI 能写多少代码"，而在于揭示了一件事——决定上限的，从来不是模型本身，而是模型之外的那套东西。那套东西，叫 Harness。

这篇文章想把"Harness Engineering"这个已经被讲得有点泛的概念，从三个层面重新讲清楚：

- **它是什么**——一次工程范式的进化，以及一个简单到可以写成公式的定义；
- **它怎么落地**——把抽象方法论拆成目录、脚本、角色和流程，一步步搭出来；
- **它通向哪里**——当缰绳越收越紧，我们最终会发现自己手里攥着的不是缰绳，而是一面镜子。

前两层是工程问题，第三层是认知问题。多数文章只讲到第二层就收尾了，但真正让人后背发凉的，恰恰是第三层。

---

## 一、定义：Agent = Model + Harness

Harness，字面意思是"马具"——缰绳、鞍具、辔头。没有马具的马，再快也只是信马由缰；套上马具，才能指哪打哪。

放进 AI 工程语境里，这个比喻精确得惊人。它可以压成一个公式：

> **一个完整的 AI Agent 系统，除了大模型本身之外的所有东西，都属于 Harness。**

Prompt、Context、工具、规则、验证脚本、多 Agent 调度、记忆、知识库……模型是那匹马，其余一切是马具。Harness Engineering 研究的，就是如何为一个能力极强但天生没有规矩的模型，设计出一套合适的装备，让它在真实工程里**持续、稳定、规范、顺畅地产出你真正想要的结果**。

注意这句话里的三个关键词，它们界定了 Harness 真正解决的问题：

- **稳定**——不是这次运气好做对了，而是换个需求、换个维护人、过几个月，它仍然能做对；
- **产出**——不只是写代码，还包括需求、方案、验证、交付的完整过程产物；
- **正确**——不是"做完了就算"，而是最终有办法判断它到底做得对不对。

所以 Harness Engineering 真正回答的不是"怎么让 AI 更聪明"，而是：**怎么把一个会临场发挥的模型，变成一个可约束、可协作、可校验、可持续维护的执行系统。**

## 二、进化：Prompt → Context → Harness，三次进化的逻辑

要理解 Harness 为什么是"现在"才浮现的命题，得把工程史往回倒两步。

### 第一次进化：Prompt Engineering——"我该跟模型说什么"

大模型的底层逻辑是一个极擅长续写的系统：给它输入，它预测最可能的后续。问题在于，**"最可能"不等于"你想要的"**。给同一句"帮我写封道歉信"加上不同约束，结果天差地别。这个"加约束"的过程就是 Prompt Engineering——零样本、少样本、思维链、角色扮演、提示链……

但它有宿命。当模型从 GPT-3 进化到 GPT-4、Claude 3，语言理解能力足够强之后，"写好提示词"的边际收益急剧下降。更深的问题随之浮现：**即使模型听懂了你的话，它依然可能答错——因为它根本不知道某些关键信息。**

### 第二次进化：Context Engineering——"模型回答时该知道什么"

一个思想实验：你雇了全世界最聪明的助理，但他记忆只有 7 秒。每次见面都得重新建立对你的了解。你会怎么办？——每次见面前递给他一份简报。这份简报，就是 Context。

Context Engineering 要解决的是"信息注意力"问题，它发展出几件核心武器：

- **RAG**：不存知识，存索引。需要什么临时检索、精准注入，而不是把所有规范塞进 System Prompt 把窗口撑爆；
- **上下文压缩**：对抗"中间遗忘"（Lost in the Middle）——滚动摘要、重要性评分、层次记忆；
- **单一事实来源（Single Source of Truth）**：强制把决策、规范、文档归档进代码仓库，让 AI 的信息来源唯一、可追溯、版本受控。

OpenAI 的实战印证了这一点：他们把塞满所有规范的巨型 `agent.md` 压缩到百行以内，只当索引目录，需要哪条规范就动态加载——结果模型的遵从度和输出质量显著提升。

### 第三次进化：Harness Engineering——"整个系统该如何可靠运转"

但即便 Prompt 写得再好、Context 给得再精，下面这个场景仍然会发生：

> 你让 Agent 写一个登录模块。一小时后回来——登录逻辑对了，但它"顺手"重构了你没让它碰的数据库层；它声称测试通过，实际根本没跑；命名风格和项目其他部分完全不一致；还生成了三个功能重复的工具函数。

这些问题的根源，不在"说什么"或"给什么信息"，而在于**系统层面缺乏约束、验证和反馈机制**。这是前两次进化共同的盲区，也是第三次进化要填的坑。

三者的关系不是替代，而是**嵌套**：

| 进化 | 回答的问题 |
|---|---|
| Prompt Engineering | 我该跟模型说什么？ |
| Context Engineering | 模型在回答时该知道什么？ |
| Harness Engineering | 整个 AI 系统该如何可靠地运转？ |

没有好的 Prompt，Context 注入的信息无法被正确理解；没有好的 Context，Harness 里的 Agent 在信息真空里瞎跑；没有好的 Harness，再好的 Prompt 和 Context 也只是沙滩上的城堡——单次输出再漂亮，复杂任务里 Agent 仍会累积错误、最终崩溃。三者层层包裹，缺一不可。

## 三、落地：把方法论拆成目录、脚本、角色和流程

"理念我懂了，可第一步到底该做什么？"——这是 Harness 最该被回答、却最常被回避的问题。下面以一个真实工程（一个完全交给 AI 实现和维护的 WPF 桌面工具）的演化路径为线索，把抽象拆成可执行的零件。

### 3.1 先分清几个最容易混淆的零件

很多人一上来就写 Rule、拆 Agent、接 MCP，越做越乱，根因往往不是执行力，而是**概念没分清**：

| 零件 | 解决的问题 | 类比 |
|---|---|---|
| **Rule** | 什么事绝对不能乱来 | 研发制度、红线、底线 |
| **Skill** | 这件事具体应该怎么做 | 固定动作的标准操作手册 |
| **Sub Agent** | 复杂任务由谁分工 | 不同阶段的专业角色 |
| **Workflow** | 这些角色按什么顺序接力 | 接力赛规则 |
| **Scripts** | 谁来判断到底做没做好 | 统一门禁、事后验收 |
| **MCP** | AI 怎么安全接上外部系统 | 接入更大工程的标准插座 |

关键认知：**这几个零件不是互相替代，而是逐层叠加。** Rule 是软约束（AI 理论上该遵守，但会忘、会觉得"无关"、会偷懒找理由），Skill 把高频动作标准化，Scripts 才是硬门禁——它不是"告诉 AI 该怎么做"，而是直接检查它"做没做到"。

### 3.2 真正的第一步：不是写 Rule，是磨 SPEC

很多人一听 Harness 就想先写 Rule、先拆 Agent。但如果连"这个工程到底想怎么开发、最终交付什么"都没说清楚，后面所有约束都是无源之水。

所以真正的第一步是和 AI 反复磨一份**设计规格文档（SPEC）**：这个版本要解决什么问题、哪些是核心目标哪些只是顺手优化、改动影响哪些模块、哪些行为必须兼容、什么样才算做完。一份好的 SPEC 必须没有任何不确定词语——没有"建议""可以""推荐""可选"。这一轮你偷懒，后面会用十倍时间还回来。

但很快你会发现：只靠 SPEC，AI 还是会出问题——它不会 100% 照文档执行，做完你也很难知道它到底做到哪了，很多错误它会反复犯。SPEC 只能解决"知道做什么"，解决不了"如何稳定地做到位"。于是进入下一步。

### 3.3 演化的真实路径：哪痛补哪

值得强调的是，这套系统**不是一开始就设计好的完美体系，而是在真实问题里一轮轮撞墙、补洞长出来的**：

1. **上 Rule**——把容易忘、容易错的底线写死（"改完必须编译、测试、验证"）。粗糙问题立刻少很多，但 Rule 会被忽略、被绕过；
2. **下沉 Skill**——把编译、测试、验证这类"步骤固定、每次都做、做错很恶心"的动作做成标准手册。Rule 由此变轻，只保留红线；
3. **拆多 Agent**——当单 Agent 在长链路里同时扮演需求、方案、开发、自审、测试多个角色而开始失稳时，把它拆成结构化的固定角色；
4. **补 Scripts 门禁**——当 Rule 这种自然语言约束被"解释性执行"绕过时，把能判定的约束落成脚本，再加"开发前后基线对比"防偷懒；
5. **抽流程定义文件 + 角色契约**——当流程本身开始难维护时，把散在长文里的阶段、迁移边、回退条件、每个角色的输入输出，抽成可单独维护、可校验的资产；
6. **补项目级索引**——当进入持续迭代时，补 dev-map（开发导航图）和任务看板，让 AI 带上"整个项目的记性"；
7. **接 MCP**——当要把闭环从"开发完成"推到"可交付、可发布"时，再接构建、签名、制品、发布这些外部系统。

给新手的最小起步建议就藏在这个顺序里：**先让 AI 知道该做什么，再让它知道必须怎么做，再让它在复杂任务里学会分工，最后让流程本身变成可维护的工程资产。** 不要贪大，不要一步到位，从你最反复、最痛的那个问题开始。

### 3.4 为什么多 Agent 一定走向"结构化调度"

当单 Agent 失稳，有三条路：继续强化单 Agent（角色冲突无解）、去中心化自由协商（灵活但路径不稳、责任不清、难维护）、**结构化调度**（明确角色分工、明确流转规则、可审计、易沉淀文档）。

真实工程最后几乎都会坚定选第三条。理由很冷峻：**真正贵的不是 token，是失控。** 一个典型的七角色拆法——

> PM（只路由不越界）→ 需求分析 → 方案设计 → 闸门总控（可行性把关）→ 开发实现 → 代码审查 → 测试验证

——每个角色解决的都是前一个角色解决不了的问题：需求分析解决"想做什么"，方案设计解决"打算怎么做"，闸门解决"现在能不能做"，开发解决"真正做出来"，审查解决"是不是按要求做的"，测试解决"做出来的到底能不能用"，PM 解决"整条链怎么有序串起来"。

这里有两条踩出来的血泪铁律：**下游不能直接改上游文档**（否则责任边界全乱，只能提阻塞项由 PM 打回）；**PM 只能是"总路由器"，不能变成"总专家"**（一旦越界给专业意见，多 Agent 就退回成"一个中央大脑说了算"的旧路）。

### 3.5 最被低估的一块：事后验证

如果从整套 Harness 里只挑一个最容易被低估、价值却最高的模块，是**事后验证（总验证脚本）**。

因为它补上的不是一个步骤，而是一整个**反馈闭环**。在它之前，系统经常停留在"任务完成幻觉"里——代码改了、文档写了、AI 还自己说"已验证通过"，但系统本身并不知道这次产出到底是对、是错、还是只是看起来像完成了。

它把"完成"的定义从主观汇报变成客观结果：

> 不再是"我觉得我做完了"，而是"脚本判定你通过了，你才算做完。"

这是一个质变。从这一步开始，Harness 才第一次具备"结果感知能力"，才真正形成"做事 → 校验 → 发现问题 → 回退修复 → 再验证"的完整回路。

### 3.6 四块拼图

把上面所有零件拉远看，整套 Harness 是四块互相咬合的拼图：

- **约束与流程**（Rule / Skill / 多 Agent / Workflow）——AI 按什么节奏、什么纪律、什么边界做事；
- **反馈**（总验证脚本）——做完之后系统能不能对结果"有说法"；
- **知识库 / 索引**（dev-map / 任务看板）——这座工程"从哪读起"，让 AI 别在已建好的城里重复铺路；
- **进化**——人定方向与验收、AI 在规矩里高密度落地，把实践里长出的结论持续灌回前三块。

缺一块，症状都很典型：只有流程没反馈 → 完成幻觉；只有反馈没流程 → 失败日志收敛不成可维护的改法；没有知识库 → 同类功能反复重写、同类坑反复踩；没有进化 → 前三块冻在某一版，脚本不收紧、地图与结构脱节、改法长期堆在会话里落不回仓库。

## 四、衰变定律：模型越强，Harness 越薄

讲到这里有个反直觉但极重要的规律，来自 Anthropic 的观察：

> **模型能力越强，所需的 Harness 越简单。**

Claude 3.0 时代，为防止 Agent 在复杂任务中途崩溃，需要极严格的约束：逐个功能点执行、频繁重置上下文、大量硬编码检查。但升级到 Claude 3.5，其全局统筹、长上下文、自我校验能力大幅提升后，原本不可或缺的许多规则自然变得多余。

这条定律有两层深意，能让你避开两个相反的陷阱：

- **它是当下的现实答案**——模型尚未完美的今天，不做 Harness 就是放野马在生产环境横冲直撞；
- **它可能是过渡性技术**——模型正在逐渐"内化"这些系统规则（自动识别优先级、自动验证、自动处理边界）。

由此得出最值钱的实践原则：**不要过度设计那些模型未来能自我解决的问题。** 把精力集中在两类场景——模型短期无法靠自身解决的**业务逻辑边界**（行业规则、合规、复杂系统协同），以及模型再强也无法自行建立的**外部环境接口**（工具调用、API 集成、权限控制）。

随时问自己两个问题：
1. 这个约束是因为模型能力不足而存在，还是业务逻辑本身需要它？
2. 如果下一版模型强 20%，我的 Harness 里哪些部分可以被简化？

**谁能根据模型能力边界，动态调整 Harness 的"薄厚"，谁就在工程效率上拿到最高回报。**

## 五、人的位置：Human Steer, Agents Execute

很多人误以为 Harness 搭好后人就退场了。**恰恰相反——Harness 越强，人越重要，只是职责上移了。**

人从"执行者"变成"系统设计者"和"最后责任人"，核心职责变成三件事：

- **定方向（Steering）**：清楚要建什么、为什么建、最终形态是什么——这需要产品思维、系统思维、业务洞察；
- **搭架子（Harnessing）**：为 Agent 构建可靠支架——规则、可信上下文、自动化验证与反馈回路；
- **做判别（Decision Making）**：在关键架构点、技术路线点、风险边界点人工介入确认。

衡量一个工程师的标准也在悄悄切换：从"个人产出"（每天写多少行、能处理多难的 bug）切换到"**系统杠杆**"（能设计多健壮的 Agent 系统、能构建多完善的自动闭环、对 AI 系统失效模式理解多深）。

> 软件工程没有消失，它在进化——从"写代码的人"，进化为"设计让 AI 把代码写好的系统的人"。

关于 Memory 也值得补一句：在团队级、要长期维护的工程里，Memory 可以靠边站。纯个人偏好用 Memory 减少摩擦无可厚非，但**凡是会变成"团队都要遵守"或"交付要对齐"的东西，都不该长期停在会话记忆里**——它们该晋升进仓库：能判定的进 Scripts，不能判定的进 Rule。因为交接、审计、CI 都看不见 Memory。一句话压住分工：**事实像档案，例子像故事，规矩像手册——手册应进仓库。**

## 六、尽头：缰绳的另一头，系着的是你自己

到这里，工程层面的故事讲完了。但如果在某个深夜回头看你为 AI 写下的那份 `project.md`，会发现一件后背发凉的事——**那根缰绳的另一头，系着的不是 AI，是你自己。你手里攥着的不是缰绳，是一面镜子。**

### 6.1 第三次"显形"

人类学家 James C. Scott 在《Seeing Like a State》里提出过一个概念：**Legibility（可读性 / 显形）**——一个复杂对象只有先被系统"看见"，才能被管理、被规模化。近代以来，森林被显形（科学林业按网格种植）、人群被显形（统一门牌登记）、手艺被显形（拆成工序与秒表时间）。每一次显形都是文明的跃升，也是一次隐秘代价的清算。

前两次显形，看的是"别人"。**这一次，AI 把镜子转了过来，对准了我们自己。**

当你给 AI 写一份 `project.md`、一条 Rule、一份 Spec，你就是在**强迫自己把最不愿说出口、最说不清的那部分，说给一台机器听**。过去四十年软件工程无数次"知识显形"的尝试（UML、DDD、ADR、Wiki）都失败了一半，因为写文档成本高、收益低、没人读。AI 改变了两件事：

- 文档第一次有了**一个永不疲倦、永不遗忘、永远会读的读者**；
- **AI 不理解潜台词**——你对新同事说"这块别动"他会心领神会，对 Agent 说"这块别动"它会追问：不能读还是不能改？重命名变量算改吗？

这一连串追问，就是显形运动在你身上发生的瞬间。写 Spec，不再是"整理已经想清楚的事"，而是被一个永不疲倦的读者**逼着把自己从未想清楚过的事想清楚**。这不是效率升级，是一次认知事件。

显形按从浅到深的顺序穿透研发三层：**意图层**（"我想要什么"被迫写成可执行文本）、**执行层**（老师傅脑子里七步走的隐性知识被写成可 diff、可 review、可 rollback 的流程节点）、**判断层**（"做得好不好"被送上祭坛）。前两层是温柔的，最后一层是危险的。

### 6.2 Goodhart 与不可能三角

判断层为什么危险？因为"好"是计算机科学至今没攻克的最难的字。让十个资深工程师评同一段代码，会得到十个都有道理的答案。但 AI 写代码的速度已远超人类 review 的速度，**判断必须被显形**，否则整条"意图→执行"的链路在最后一公里断掉。

可一旦显形，就撞上 **Goodhart 定律**：

> 当一个度量变成目标，它就不再是一个好的度量。

要求"通过这 100 个测试"→ AI 精确通过这 100 个、对边界毫不关心；要求"覆盖率 > 85%"→ 生成大量 `assert True` 刷分。这不是 AI 变坏，是所有优化系统的本性。更深一层，经济学家 Arrow 早在 1951 年就证明：**任何把三个以上维度聚合成单一总排序的机制，都必然违反基本公平性——"综合评价"从数学上就不可能。** 那种"性能 30% + 可读性 30% + 安全 40%"的加权评分，注定让所有人都不满意。

由此可以写出一个**判断工程的不可能三角**：

> ① **Spec 完备性**（所有"好"都写下来，不留模糊）、② **Goodhart 抗性**（标准不被优化得面目全非）、③ **Tacit 保全**（无法言说的直觉、审美、禁忌不被抹除）——**三者不可兼得，最多同时满足两个。**

- 要 ①②、舍 ③：写死一切、全员合规，但老师傅沉默，代码正确却没有温度；
- 要 ①③、舍 ②：KPI 和 Eval 堆到眼花，分数涨了线上事故反而不降；
- 要 ②③、舍 ①：拒绝写任何规则（"这种事说不清"），AI 根本跑不起来。

所谓工程智慧，不是抵达三角形的中心（那个点不存在），而是**清楚自己扎营在哪条边上，并承认另一条边的代价**。

### 6.3 黑森林的一百年

18 世纪的德国，管理者把杂乱的天然林清掉，换成按网格种植、按材积表测算的同龄单一林——人类第一次"科学森林"。第一代惊艳：产出稳定可控，全欧洲来学。第二代塌方：土壤退化、虫害爆发、一场风暴刮倒成百上千公顷。整整一个世纪后才被迫转向"近自然林业"。

它的悲剧不是"材积没提升"——提升了。它的悲剧是**把"森林"这个词的定义，悄悄窄化成了"木材产出"**。一百年后人们才发现：森林原来比木材多得多。那些没被度量的东西——土壤微生物、食物链、生态异质性——恰恰是让整个系统活着的东西。

AI 时代正面临结构一模一样的风险：**我们正在把"好代码"悄悄窄化成"能通过一组 Eval 的代码"。** 我们看不见的，可能是那些没测过却稳定跑了十年的隐性约束、那些 review 时"说不出哪里不对但就是不对"的皱眉。

> 这场显形运动的危险不在于它想看见一切，而在于：它只能看见一部分，但我们会误以为看见的就是全部。

### 6.4 三块石碑，与刻意不刻的地方

不能不显形，就把显形做得更聪明一点。先承认**判断力不是一个点，是一段光谱**——从 S1 硬规则（Lint、编译）、S2 量化指标（覆盖率、圈复杂度）、S3 结构化规格（验收标准、行为契约）、S4 偏好陈述（"我们偏好 X 胜过 Y"）到 S5 裸直觉（"就是觉得不对"）。成熟团队的标志不是把一切推向 S1/S2，而是**清楚每件事该落在哪一档**——把合规放到 S4 是失职，把代码审美写成 S1 是暴力。

对应地立三块石碑：

- **验收标准即代码**：把"什么叫做完了"写成可进 CI、可 diff、可演化的文本，用业务语言写、与代码同 PR、标准本身也要被评审——让"意图"第一次成为被评审的一等公民；
- **对抗性审查网络**：让"做事的"和"审事的"永远不是同一个 AI，对抗 LLM 的自洽偏差（self-consistency bias）——系统的健壮性来自认知多样性，而非认知一致性；
- **品味作为资产**：给项目写一份 "Project Taste" 文档，记录那些**带偏见的偏好**（"继承不超过两层""拒绝 V2/V3 命名""宁可多写一次也不在业务边界处复用"）。它们不保证 100% 被遵守，但能让 AI 产出的代码"闻起来像这个团队的代码"——影子不是本体，但影子总比没有好。

但永远别把石碑刻满整座大陆。博尔赫斯写过一张 1:1 的地图，它和帝国完全重合，于是毫无价值——因为它就是帝国本身。**"完美的显形"等于"没有显形"。** 所以要留出四处刻意不刻的地方：战略方向感（外包了人就没意义）、价值观底线（其精髓恰恰是在规则沉默处说话）、肉眼的禁忌（"别在周四下午发版"，一旦被理性化就失效）、审美的争论（两个工程师为代码好不好看吵一下午，这个过程本身就是组织的健康信号）。

---

## 结语：带疤痕的判断

回到那个百万行代码的实验。那 3–7 名工程师的价值，没有一个体现在"手写代码的速度"上，而体现在他们搭建的那套 Harness——那套让 AI 能持续、可靠、高质量产出的"驾驭装置"。

但 Harness 的尽头不是缰绳。当我们把意图、执行、判断一层层显形进仓库，最终会撞上一个无法外包的东西：

> AI 永远不会真的"后悔"。它不会半夜三点躺在床上想起三年前那次线上事故，然后第二天看 PR 时多问一句"这里你考虑过并发吗"。

**"带疤痕的判断"——这是人类在 AI 时代最根本的护城河。** 不是因为 AI 无法模仿，而是因为真正的判断力来源于面对不确定性时的承担意愿，这必须由一个有身体、有代价、有后悔的主体来完成。

所以 Harness Engineering 这件事，往小了说，是教你怎么从最痛的那个问题开始，把规矩、技能、脚本和流程一点点沉进仓库；往大了说，是这个时代每一个在 `project.md` 上写下第一行字的人，正在做一件人类文明第一次做的事——**把自己看不见的那部分自己，第一次写给另一种智能看。**

人不退守，人转身。
