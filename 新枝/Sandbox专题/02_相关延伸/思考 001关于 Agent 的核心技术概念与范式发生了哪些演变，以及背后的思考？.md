这篇文章主要讲的是 Agent 从 Chatbot 到现在的 Autonomous Agent 的变化趋势。

很显然，它不是一开始就发展成这样的，而是一点点继承、一点点演进。虽然中间的探索方向现在看起来五花八门，但我们不要为了追求最新的架构而盲目升级，否则会导致 ROI 比较低。

不过，新的架构还是需要学习的，毕竟你不去尝试的话，也很难知道它具体有什么作用。
从开始到现在，Agent 的发展主要经过了四个阶段的划分：

1. 早期阶段：被动 React 模式
   早期的 Agent 本质上是一个被动的 React 模式，只能接受输入并观察输出。输出过程需要人工干预，并逐步进行试错。它的形式类似于聊天机器人（Chatbot）。

2. 工作流阶段（Workflow）
   这个阶段引入了状态机，将一些固定的流程引入工作流中，使其变得可控。但缺点是，一旦遇到流程之外的不可控结果，工作流就可能陷入死循环，导致系统失效。

3. 自主 Agent 阶段（Autonomous Agent）
   如果说前两个阶段更多被视为 Chatbot，那么这个阶段则是 Agent 迈向自主化的第一步。它能够执行复杂的、长流程的任务，比如进行深度研究（Deep Research）或编写代码（Coding）。
   (a) 典型的代表如 Anthropic Claude 也是在这个时期开始成长起来的。
   (b) 它具备了环境感知、目标设定、上下文理解和子任务拆解的能力。

4. 自进化 Agent 阶段
   也就是我们现在所处的“阶段 4”。这个阶段的 Agent 能够实现自进化，原因在于它具备持续学习和自我升级的能力。
   (a) 它能实现记忆的沉淀、更新以及策略的优化，这种特性已经有点偏向 AGI（通用人工智能）。
   (b) 每次运行的数据都能存储起来，供下一次使用。
   (c) 另一个关键点是，自进化 Agent 模糊了训练阶段和工程阶段的界限，在后期工程应用的过程中也能不断进行训练和学习。
下面详细拆解一下这四个阶段：

5. 早期 Agent 阶段
   (a) 本质上是一个被动式的 ReAct 架构。其基本架构包括 Memory（短期记忆与长期记忆）、Planning（规划）、Tools（工具）和 Action（执行）。
   (b) 规划能力类似于我们之前提到的思维链（CoT）及其反思机制；工具方面则是通过调用函数来接入外部能力。
   (c) 它更像是一个增强版的 Chatbot，虽然引入了思维链，但只能完成一些单点的小任务，缺乏长期规划的能力。

6. 工作流 Agent（Workflow Agent）阶段
   (a) 这一阶段更关注结构化与可控性。通过预先编排的方式演进，让 Workflow 运行得非常稳定。
   (b) 这种方式类似于早期的 Harness，通过增加约束来引导 Agent 的行为。虽然牺牲了一定的灵活性，但带来了极高的可控性和可解释性。
   (c) 在 To B 领域非常受欢迎，因为它能处理大量重复性、流程化的工作。对于非极度复杂的场景，这是目前性价比最高、落地最稳的方案。

7. 自主 Agent（Autonomous Agent）阶段
   (a) 具备处理复杂规划和长任务的能力。从最初的 Magnus（通用的 Agent），演进到像 Cloud Code、Codex、A-Coding 这种更专业的 Agent。
   (b) 这一阶段的 Agent 能够调用多种工具并直接给出结论，支持长任务执行。
   (c) 我们可以为其设定一些 Spike（例如开发规范），让它自动执行。此外，它还具备轻度的 Harness 能力，能够实现自我校验并交付成果。

8. 2026 年以后的自进化阶段
   (a) 随着 Harness Agent 的兴起，通过沉淀 Skill（技能）以及引入强化学习，Agent 将进入一个更加资讯化、智能化的阶段。
   (b) Agent 从一次性的 Chatbot 对话流，转变为一种可积累的资产。
   (c) 这种模式将为 AGI、长期的数字员工以及 Open Cloud 等领域提供重要的能力互补。后面我们来看一下几个演进过程中的概念，比如 Prompt、Planning、Memory、Tools、Workflow、Environment，或者叫 Runtime。我们来看一下它有哪些变化。

首先是 Prompt。Prompt 是我们接触最早的一个词汇，在这个时候，每个任务都会有一个对应的 Prompt。比如说写文章的 Prompt、编辑文章的 Prompt、润色的 Prompt，甚至还有一些生成图片的 Prompt。在这种模式下，每个任务独立写一个类似于小的 Chatbot 形式。但是，这种产品增多的话，会变得比较混乱，很难管理。

随着近两三年的深入实践，Prompt 变成了静态和动态两个方面。静态的 Prompt 我们可以理解为系统指令层级，它会尽量固化 System Prompt，然后把动态的具体任务剥离出来。动态的 Prompt 现在主要有两个方向：
1. Skill 层面的沉淀。这包括完成任务所用的步骤、方法、规束、约束等，比如 `Skill.md` 或者一些 Markdown 文件。
2. 配置文件存储。Cloud 做得比较好，它会有 `User.md`、`Soul.md`、`Cloud.md` 这种配置文件。其实这也算是整个外部文件系统，可能会包含 Skill、知识库或者资源库这种东西，它能够渐进式地披露或者加载进来。

第二个是 Planning。Planning 这个规划在早期只有 COT。也就是说，它根据每一步的输出去规划下一步的输入以及思考方式，让它按照 Step by Step 这种方式去执行。但是，后面因为它很容易断层或者死循环，一旦遇到一些复杂的场景就可能不 work 了。现在由于模型能力，尤其是 Reasoning 模型变得越来越强，它可以做一些结构复杂问题的分解。比如说，可以把它拆分成 Spike 这种东西，或者 N 多个子目标，然后去协同。另外，这种长任务有了执行计划，它能够按照这种执行计划去保持逻辑的一致性和连贯性。

子 Agent 的话，就是当它需要某个事情的时候，可以用一个子 Agent 去把它完善。关于一致性、连贯性，还有子 Agent 的这种感觉，这个还在发展，未来可能会变得不一样。它可能 Reasoning 模型变得足够大之后，就不需要做拆解了。

第三个是 Memory，也就是检索增强。Memory 短期的话就分成短期记忆和长期记忆，有 Short-term memory 和 Long-term memory。短期记忆就是当前的上下文，包含 System Prompt、User 历史对话的 User 和助手的回复。长期记忆就是通过 RAG，用 RAG 从知识库之中加载的相关文件或者知识库，本质上是给它做一个运行时的环境。

现在这种管理方式变得太复杂了，也是大家对话越来越多，大家可能是要管理和组织当前的 Memory。比如短期层面，可能变成了除了简单存储，还包括管理和压缩。因为它的 Context Window 是比较有限的。虽然说现在上下文一直在变，但本身大模型就会有那种 Loss in middle 这样的弊端。它更关注的是长尾，就是首尾的这种能力。从 Open Cloud 或者 Harness 这种实践的地方来看，上下文这种简单堆积历史对话的话，可能会比较有问题。所以会演变出了一些记忆压缩的策略：
1. 阈值的控制。到了多少 Token，或者到了一些动态的语义密度阈值来触发压缩。
2. 结构化摘要。就是对过程中的对话做 Summary，确保核心的意图还在。
3. 重点提取。这本质上都是在精简短期 Memory，给后面的对话留更多的记忆窗口。

而长期记忆的话，就是变成了由相应数据库主导，变成了文件系统主导。为什么是这样的呢？因为事实性的记忆，原来的框架通过用户的偏好、历史行为、每日待办这种，大家都通过一些文件系统来记录，比如说各种 MD 文件。当然 MD 现在可能也有人说会用 HTML，这样的话它能更好地读，可能读图片或者读一些标签更好读。但是这些 HTML 本质上也会输入更多的上下文窗口，因为它有很多的标签语言。另外，这主要是像一些 Open Cloud 这种带起来的。

知识型的记忆，这是 Karparse 这个 LRM 的人提的，他主要是说从本地文件系统加 Obsidian 这种笔记工具，它就像一个图数据库。然后它会通过 Grip 这种关键字。这个可能在演进吧，Memory 这个东西。但是 Memory 这个东西它可能有点类似于人的 Memory，你记了很多，但它可能跟这次任务不相关。如果说它能够把所有的 Memory 都结合起来的话，做出的决策可能不符合人类的第一直觉，不过它可能符合 Agent 的最好优势。

下一个是 Tools。Tools 的变化很大。早期是 Function Call，调用一些函数。现在 Tools 变成了 CLI 命令行，它能够做系统操作、文件处理、网络请求、DevOps 这种多动作。另外，Script 脚本可能附着在 Skill 里面。它相对于之前的接入方式，还有一些可控以及上下文的捕捉，这都会比之前的 Function Call 要更好一点。OK，接着看一下 workflow 这个东西。

从 workflow 变成 skill 之后，它主要有以下改进：
1. 能够更专业地用计算机语言——即“高内聚、低耦合”以及“可重用”的标准来调整。
2. 实现了可复用与低依赖：每个 skill 各司其职，同时也能更好地解决一些 workflow 无法处理的问题。
3. 稳定性差异：对于更规范、更具确定性的任务，workflow 依然更稳定；而 skill 可能会存在一些不太稳定的地方。

另外一点是 Environment（或者叫 Runtime）的变化。之前可能没有环境的概念，只是一个一次性的 Chat 和流；现在则变成了一个类似于 Editor 的 Workspace。根据其框架来看，它具备了以下能力：

1. 基础系统支持：
   (a) 文件系统
   (b) 日志系统（如运行日志、错误日志等）
2. 状态管理：包括规划状态、任务状态、上下文进度等。
3. 资源管理：
   (a) Skill Memory 与模型的配置
   (b) 模型网关与工具配置
   (c) API Key 认证等
4. Sandbox（沙箱环境）：能够实现代码执行、网络访问以及资源限制隔离。

总而言之，这些改进都是在最大化地释放模型的推理能力和潜能。
