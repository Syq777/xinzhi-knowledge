构建可进化的 Agent 评估体系：一篇笔记的完整总结



这篇笔记的核心是讲，评估 Agent 的标准（Rubric）不能只停留在“打分”，而应该成为驱动系统自我完善的“中枢神经”。它提出了一套构建“自进化” Rubric 的完整方法论。



核心目标：从“评分”到“可修复的诊断”



Rubric 的最终目的不是给出一个分数，而是让系统从失败中“吸收教训”。分数本身毫无意义，只有当它能被转化为可回放的错误案例（eval case）、可验证的断言（assertion）、候选补丁（patch）并最终写回资产（如 prompt, tool, workflow）时，评分才创造了价值。



设计原则：七个关键“因为”



笔记详细阐述了构建这套体系需要遵循的七项基本原则，确保评估体系本身是合理且可执行的。



维度拆解到原子级，定位责任



传统的复合维度（如“回答是否准确、完整、清晰”）无法定位问题。必须拆解到原子级，确保每个维度只回答一个问题，并指向唯一的修复方向。



硬验证先于语义判断，分层校验



能用规则、数据库等确定性方式检查的问题（如 JSON 格式、金额范围），就不应该让 LLM 来判断，以此分层来控制成本和风险。



过程与结果并重，Trace 作为诊断依据



Agent 的风险藏在执行过程中。只看最终回答（Outcome）是片面的，必须结合记录全过程的 Trace，检查工具选择、参数、依赖顺序等是否合理。



证据契约先行，允许“未知”



Rubric 必须先定义好评判需要读取哪些字段（Evidence Contract）。如果关键证据缺失，评分者（Judge）必须返回 unknown 而非猜测，这能暴露系统链路的问题。



标准需具体化，避免通用模糊



不能使用“该模型是否理解用户意图”这类无法验证的通用标准。必须将标准与具体任务、示例、工具描述等资产绑定，使其可被验证。



区分“裁判”与“教练”，不同模式不同对待



LLM 作为“裁判”（事后打分）和“教练”（事中引导）时，评估重点不同。笔记引用研究指出，裁判模式下即使提示词相同，也存在位置偏差、长度偏差等系统性问题，需要谨慎处理。



Rubric 本身亦需进化，纳入闭环



评判标准（Rubric）本身也是一种系统资产，会因业务、模型、用户预期的变化而“老化”。因此，Rubric 自身也必须进入“评估-校准-回写”的自进化闭环，通过人工复核来发现和修正标准中的模糊地带。



总结：从“会评价”到“能进化”



最后，作者用一句话总结了这套方法论的核心标准：一个自进化系统的核心标准，不是“JUDGE 准不准”，而是“JUDGE 能不能稳定地产生可修复信号”。这要求评估体系本身是可被验证、可归因、可修复且可回测的。
